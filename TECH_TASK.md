# Product & Technical Specification
## Локальный Delivery Planner с Gantt-таймлайном и capacity planning

**Статус:** готово к оценке и декомпозиции в разработку  
**Версия документа:** 1.0  
**Дата:** 22.07.2026  
**Целевая платформа:** Desktop Web, macOS и Windows  
**Технологическая база:** Bun + Nuxt, SPA (`ssr: false`), Nuxt UI  

---

## 1. Резюме продукта

Необходимо разработать небольшое локальное веб-приложение для управления delivery-планом команды. Основной интерфейс приложения — интерактивный Gantt-таймлайн, похожий по структуре на текущую Excel-таблицу пользователя, но с нативным управлением этапами, зависимостями, рабочим календарём и загрузкой ресурсов.

Приложение работает без серверной части и регистрации. Данные хранятся локально в браузере, автоматически сохраняются, могут быть выгружены в JSON и восстановлены из резервной копии. Для передачи плана другим людям поддерживаются экспорт JSON, PNG и печатное представление для сохранения в PDF.

Основной объект планирования — **эпик**, который в рамках приложения одновременно является проектом. Эпик содержит **этапы** трёх видов: `task`, `scope`, `milestone`. Этапы размещаются на общей временной шкале с точностью до одного дня, получают тип деятельности, зависимости, назначения сотрудников/ролей, Markdown-описание и список входящих задач.

Приложение должно отвечать на два главных вопроса:

1. **Что, в какой последовательности и в какие сроки делает команда?**
2. **Сколько capacity занято и сколько остаётся свободным в конкретный день или неделю?**

## 2. Ключевые продуктовые решения

### 2.1. Не использовать `localStorage` как основное хранилище

Изначальная идея с одним JSON в `localStorage` подходит для прототипа, но является плохой основой для рабочего инструмента:

- `localStorage` синхронный и блокирует основной поток при чтении и записи;
- он предназначен для небольших key-value данных, а не для связанной модели из эпиков, этапов, зависимостей, задач, baseline и резервных копий;
- один большой JSON усложняет частичную загрузку кварталов, транзакционность, миграции и восстановление после неудачной записи.

**Принятое решение:**

- основное хранилище — **IndexedDB**;
- доступ к IndexedDB — через **Dexie**;
- данные по-прежнему являются обычными сериализуемыми JSON-совместимыми объектами;
- `localStorage` используется только для небольших UI-настроек: выбранный квартал, масштаб, размеры панелей, тема;
- пользовательский переносимый формат — один версионируемый JSON-файл.

### 2.2. Не разрабатывать визуальный Gantt-движок с нуля

Самостоятельная реализация временной сетки, sticky-заголовков, drag/resize, dependency links, smart rendering, синхронного скролла и корректного позиционирования займёт непропорционально много времени и создаст большое число пограничных ошибок.

**Рекомендуемый визуальный движок:** **DHTMLX Gantt Community Edition 10+** под MIT-лицензией.

Он используется только как UI-движок для:

- сетки и временной шкалы;
- строк проектов и этапов;
- task/milestone bars;
- drag-and-drop и resize;
- отображения dependency links;
- масштабов времени;
- виртуализированного/smart rendering.

Критически важная бизнес-логика — каскадное планирование, capacity, baseline, квартальная загрузка и сохранение — реализуется в собственном domain-слое. Визуальный компонент не является источником истины.

### 2.3. Разделить тип элемента и тип деятельности

Это разные измерения и они не должны смешиваться.

**Вид этапа (`kind`):**

- `task` — конкретный планируемый этап;
- `scope` — укрупнённый блок работ, который пока не декомпозирован;
- `milestone` — веха без длительности.

**Тип деятельности (`activityType`):**

- research;
- design/analysis;
- development;
- testing;
- integration;
- release;
- other.

Список типов деятельности редактируемый. Пользователь может добавлять свои типы, переименовывать их и выбирать цвет.

### 2.4. Не превращать список задач этапа во второй планировщик

Задачи внутри этапа нужны для детализации scope, но не должны одновременно становиться скрытыми Gantt-элементами и повторно потреблять capacity.

В MVP внутренние задачи являются лёгкими checklist/work-item сущностями:

- отображаются внутри этапа;
- агрегируются на уровне эпика;
- могут быть не привязаны к этапу и находиться в backlog эпика;
- имеют статус и необязательного исполнителя;
- **не имеют собственных дат, зависимостей и allocation**;
- **не участвуют в расчёте capacity**.

Если в будущем потребуется детальное планирование задач, отдельную задачу можно будет конвертировать в этап.

### 2.5. Зависимости должны ограничивать расписание, а не просто рисовать стрелки

Поддерживается связь **Finish-to-Start**. Этап может иметь несколько предшественников и несколько последователей. Граф зависимостей обязан быть ацикличным.

Основной интерактивный режим — каскадный перенос связанных этапов. Дополнительно существует свободный режим, при котором двигается только выбранный этап.

### 2.6. Capacity считается из FTE, а показывается несколькими способами

Хранимая единица — **FTE**.

Пользователь видит:

- занятое количество сотрудников/FTE;
- процент загрузки;
- человеко-дни за период;
- свободный остаток capacity.

Формула трудоёмкости этапа:

`Work person-days = количество рабочих дней × сумма назначенного FTE`.

## 3. Цели продукта

### 3.1. Основные цели

1. Заменить Excel-диаграмму нативным интерактивным таймлайном.
2. Сделать перенос сроков безопасным и предсказуемым.
3. Автоматически пересчитывать связанные этапы.
4. Показывать параллельные потоки внутри одного эпика.
5. Показывать доступный и занятый capacity команды.
6. Давать единое представление по текущему и следующему кварталу.
7. Хранить данные локально и не требовать backend.
8. Обеспечить переносимость данных через JSON.
9. Позволить быстро подготовить статичный снимок плана для коммуникации.

### 3.2. Метрики успешности

Количественные продуктовые метрики не собираются автоматически, так как приложение не отправляет аналитику. Успешность оценивается по пользовательским критериям:

- актуальный план поддерживается без ручного перекрашивания ячеек;
- перенос цепочки этапов выполняется одной операцией;
- перегрузка команды видна без ручного подсчёта;
- план текущего/следующего квартала открывается за считанные секунды;
- пользователь может восстановиться после ошибочного импорта или массового изменения;
- экспортированный JSON полностью восстанавливает workspace.

## 4. Не входит в MVP

Следующие возможности осознанно исключены:

- серверная синхронизация;
- регистрация и авторизация;
- совместное редактирование в реальном времени;
- live-sharing плана по ссылке с данными;
- комментарии и уведомления;
- интеграции с Jira, YouTrack, GitHub или календарями;
- почасовое планирование;
- индивидуальные рабочие календари и отпуска;
- автоматическое распределение role-demand по конкретным людям;
- автоматическое уменьшение duration при добавлении сотрудников;
- критический путь;
- четыре типа Gantt-зависимостей;
- зависимости между разными эпиками;
- собственные даты и capacity у внутренних checklist-задач;
- полноценная мобильная версия;
- серверный экспорт PDF/PNG;
- гарантированная работа с десятками тысяч этапов.

## 5. Термины

| Термин | Значение |
|---|---|
| Workspace | Локальный набор всех проектов, ресурсов, календаря и настроек |
| Эпик / проект | Верхний уровень планирования; эти понятия равнозначны |
| Этап | Элемент на Gantt-таймлайне |
| Task | Конкретный этап с длительностью |
| Scope | Укрупнённый этап с длительностью |
| Milestone | Веха с одной датой и без capacity |
| Activity type | Вид деятельности: research, development, testing и т. п. |
| Work item | Лёгкая задача/checklist внутри эпика или этапа |
| Dependency | Связь между этапами |
| Predecessor | Предшествующий этап |
| Successor | Зависимый последующий этап |
| Allocation | Доля ресурса, выделенная этапу |
| FTE | Эквивалент полной занятости одного сотрудника |
| Capacity | Доступная рабочая ёмкость ресурсов |
| Baseline | Неизменяемый снимок плановых дат на конкретный момент |
| Working day | День, включённый в рабочий календарь |
| Quarter bucket | Логическая партиция данных по кварталу |

## 6. Пользователь и основные сценарии

### 6.1. Основной пользователь

Feature/delivery-менеджер или технический лидер, который:

- планирует эпики и этапы;
- согласует сроки;
- следит за зависимостями;
- распределяет разработчиков;
- оценивает свободный capacity;
- показывает актуальный план команде и руководителю.

### 6.2. Основные сценарии

1. Создать эпик и быстро набросать scope этапами на квартал.
2. Добавить этапы `research → development → testing → integration` последовательной цепочкой.
3. Создать параллельную ветку работ внутри того же эпика.
4. Назначить одного разработчика на одну ветку, второго — на другую.
5. Сдвинуть development на три рабочих дня и каскадно перенести зависимые этапы.
6. В свободном режиме сдвинуть только один этап и увидеть нарушение связи.
7. Посмотреть, сколько backend-разработчиков занято в конкретную неделю.
8. Открыть ячейку capacity и увидеть, какие этапы формируют нагрузку.
9. Добавить Markdown-описание и checklist задач в этап.
10. Посмотреть все задачи эпика, включая распределение по этапам.
11. Сохранить baseline перед согласованием сроков.
12. Сравнить актуальный план с baseline.
13. Экспортировать квартал в PNG/PDF для отправки.
14. Экспортировать весь workspace в JSON.
15. Импортировать конфигурацию после переезда на другой браузер.
16. Отменить ошибочный массовый перенос.

## 7. Информационная архитектура

## 8. Основной экран Timeline

### 8.1. Компоновка

Экран состоит из:

1. верхней навигационной панели;
2. toolbar таймлайна;
3. основной Gantt-области;
4. закреплённой нижней capacity-панели;
5. правого drawer для редактирования сущностей.

### 8.2. Верхний toolbar

Обязательные элементы:

- выбор квартала;
- переключатель `текущий / следующий / два квартала`;
- масштаб `день / неделя / месяц`;
- кнопка `Сегодня`;
- режим перемещения `Каскад / Свободно`;
- undo / redo;
- фильтры;
- переключатель отображения baseline;
- кнопка создания эпика;
- кнопка создания этапа;
- меню import/export;

### 8.3. Левая часть Gantt

Отображает иерархию:

```text
Эпик
  Этап 1
  Этап 2
  Этап 3
```

Колонки по умолчанию:

- название;
- activity type;
- статус;
- назначения;
- количество checklist-задач `done/total`.

Ширина левой панели изменяется мышью и сохраняется в настройках.

### 8.4. Строка эпика

- сворачивается и разворачивается;
- показывает название и общий временной диапазон;
- в свёрнутом состоянии отображает summary bar от минимальной даты начала до максимальной даты окончания;
- summary bar не является самостоятельным планируемым этапом;
- клик открывает карточку эпика;
- drag summary bar не переносит весь эпик в MVP; массовый перенос выполняется выделением этапов или командой из меню.

### 8.5. Временная шкала

На дневном масштабе заголовок имеет три уровня:

1. месяц;
2. число месяца;
3. день недели.

Дополнительно:

- нерабочие дни визуально затемняются;
- сегодняшний день отмечается вертикальной линией;
- граница квартала выделяется;
- горизонтальный скролл синхронизирован с capacity-панелью;
- вертикальный заголовок и левая панель закреплены;
- пользователь может масштабировать колесом с модификатором или кнопками toolbar.

### 8.6. Отображение видов этапов

- `task` — сплошной прямоугольный bar;
- `scope` — bar с отличающейся текстурой/пунктирной рамкой;
- `milestone` — ромб на конкретной дате.

Цвет определяется activity type, а статус — дополнительным индикатором/обводкой, чтобы не смешивать две классификации.

### 8.7. Подсказка этапа

При hover отображаются:

- название;
- эпик;
- kind;
- activity type;
- статус;
- период;
- рабочая длительность;
- трудоёмкость;
- назначения;
- количество задач;
- наличие нарушенных зависимостей;
- отклонение от baseline.

## 9. Функциональные требования

## 9.1. Workspace и кварталы

### FR-WS-001. Инициализация workspace

При первом запуске приложение создаёт пустой workspace с:

- дефолтным рабочим календарём понедельник–пятница;
- базовыми activity types;
- текущим кварталом;
- следующим кварталом.

### FR-WS-002. Один workspace в MVP

Пользователь работает с одним активным workspace. Внутренняя модель обязана иметь `workspaceId`, чтобы позже поддержать несколько workspace без полной миграции модели.

### FR-WS-003. Квартальный переключатель

Пользователь может открыть:

- текущий квартал;
- следующий квартал;
- совмещённое представление текущего и следующего квартала;
- архивный квартал через дополнительный список.

### FR-WS-004. Ленивая загрузка кварталов

В оперативное состояние загружаются только:

- глобальные справочники;
- эпики;
- этапы и связи выбранного временного окна;
- минимально необходимые связанные записи соседних кварталов.

Архивные кварталы не загружаются без запроса.

### FR-WS-005. Этапы на границе кварталов

Этап может пересекать границу квартала. Он хранится в одном экземпляре и получает список квартальных bucket ID, с которыми пересекается. При отображении двух кварталов дублирование запрещено.

## 9.2. Эпики

### FR-EP-001. Создание эпика

Поля:

- название — обязательное;
- короткий код — необязательный;
- Markdown-описание — необязательное;
- статус: active / paused / done / archived;
- цвет/маркер — необязательный;
- сортировочный индекс.

### FR-EP-002. Редактирование эпика

Редактирование выполняется в правом drawer или на странице эпика.

### FR-EP-003. Удаление эпика

Удаление требует подтверждения. Пользователю показывается количество этапов, задач, зависимостей и baseline-записей, которые будут затронуты. Перед удалением создаётся резервный snapshot.

### FR-EP-004. Архивация

Архивный эпик скрывается из основного представления, но остаётся в данных и доступен через фильтр.

### FR-EP-005. Страница эпика

Страница содержит:

- описание;
- статус и период;
- список этапов;
- агрегированный список внутренних задач;
- группировку задач по этапам;
- backlog-задачи без этапа;
- назначения и суммарную трудоёмкость;
- активные зависимости;
- baseline-отклонения.

---

## 9.3. Этапы

### FR-ST-001. Создание этапа

Этап можно создать:

- кнопкой;
- из контекстного меню эпика;
- drag по пустому диапазону строки;
- дублированием существующего этапа;
- вставкой из внутреннего clipboard.

### FR-ST-002. Поля этапа

Обязательные:

- `epicId`;
- название;
- kind;
- activity type;
- status;
- дата/период.

Необязательные:

- Markdown-описание;
- назначения;
- зависимости;
- checklist-задачи;
- флаг блокировки;
- заметка/внешняя ссылка.

### FR-ST-003. Даты

Для `task` и `scope` задаются `startDate` и `endDate` включительно. Для `milestone` задаётся одна дата.

### FR-ST-004. Drag-and-drop

Пользователь может перемещать `task` и `scope` по горизонтали. Перемещение снапится к календарному дню.

### FR-ST-005. Resize

Пользователь может изменять начало или окончание `task`/`scope` перетаскиванием границы.

### FR-ST-006. Перестановка строк

Этапы можно менять местами по вертикали внутри эпика. Порядок строк не изменяет граф зависимостей.

### FR-ST-007. Перенос между эпиками

Перенос этапа в другой эпик выполняется через действие `Переместить в эпик` или вертикальный drag с подтверждением. Зависимости с этапами старого эпика удаляются только после отдельного подтверждения. Межэпиковые зависимости в MVP запрещены.

### FR-ST-008. Блокировка

Заблокированный этап:

- не перемещается автоматически;
- не перемещается drag-and-drop;
- не меняет размер;
- может быть изменён только после явной разблокировки.

### FR-ST-009. Статусы

Поддерживаются:

- Planned;
- In progress;
- Done;
- Blocked.

## 9.5. Зависимости и планирование

### FR-DP-001. Тип зависимости

В MVP поддерживается только Finish-to-Start.

### FR-DP-002. Lag

Связь может иметь неотрицательный lag в рабочих днях. Значение по умолчанию — 0.

При lag 0 successor начинается не ранее следующего рабочего дня после окончания predecessor.

### FR-DP-003. Несколько связей

Этап может иметь несколько predecessors и successors.

### FR-DP-004. Создание связи

Связь создаётся:

- drag от dependency handle одного bar к другому;
- выбором predecessor в drawer;
- автоматически при последовательном создании этапов, если включён `Auto-link new stages`.

### FR-DP-005. Удаление и изменение связи

Пользователь может удалить связь, заменить predecessor и изменить lag.

### FR-DP-006. Защита от циклов

Перед созданием связи выполняется проверка DAG. Циклическая связь отклоняется без изменения данных.

### FR-DP-007. Параллельные ветки

Наличие нескольких этапов в одном эпике не подразумевает последовательность. Этапы без прямой или транзитивной зависимости могут выполняться параллельно.

### FR-DP-008. Режим `Каскад`

Это режим по умолчанию.

При переносе этапа:

- определяется транзитивный граф successors;
- все связанные незаблокированные successors получают тот же сдвиг в рабочих днях;
- после сдвига выполняется нормализация ограничений с учётом всех predecessors;
- относительные gaps сохраняются, насколько это не нарушает другие зависимости;
- одна операция записывается в undo как единая команда.

При resize:

- изменение правой границы преобразуется в delta длительности;
- successors каскадно сдвигаются на соответствующее количество рабочих дней;
- изменение левой границы с сохранением end date изменяет duration и обрабатывается аналогично.

### FR-DP-009. Режим `Свободно`

Перемещается или изменяется только выделенный этап/группа. Остальные этапы не меняются.

Если после операции нарушена зависимость:

- операция разрешается;
- связь и этапы получают warning state;
- в интерфейсе отображается количество конфликтов;
- пользователь может выполнить `Исправить расписание`.

### FR-DP-010. Временный модификатор

Удержание Alt/Option во время drag временно инвертирует текущий режим:

- из Cascade в Free;
- из Free в Cascade.

### FR-DP-011. Нормализация расписания

Команда `Исправить расписание` переносит нарушенные successors на минимально допустимые даты, не меняя predecessors и заблокированные этапы.

### FR-DP-012. Компактное расписание

Отдельная команда `Сжать цепочку` переносит выбранную цепочку на максимально ранние допустимые даты с учётом predecessors и lag. Она никогда не запускается автоматически после обычного drag.

### FR-DP-013. Заблокированный successor

Если Cascade упирается в заблокированный этап, до commit показывается конфликт:

- название блокирующего этапа;
- требуемая дата;
- текущая дата;
- варианты: отменить, выполнить свободный перенос, разблокировать и продолжить.

По умолчанию операция отменяется.

### FR-DP-014. Preview каскада

Во время drag пользователь видит ghost-preview всех затрагиваемых этапов. Запись в БД происходит только после drop.

### FR-DP-015. Межквартальные связи

Зависимости внутри одного эпика могут пересекать границу кварталов. При операции движок подгружает связанные записи по необходимости.

### FR-DP-016. Межэпиковые связи

В MVP запрещены. Внешняя зависимость моделируется milestone или заметкой.

## 10. Точные правила scheduling engine

## 10.1. Формат дат

В domain-модели даты хранятся как `YYYY-MM-DD` без времени и timezone.

Запрещено хранить плановые даты как локальные midnight timestamps: это создаёт ошибки на DST и при смене timezone.

Преобразование в JavaScript `Date` выполняется только на границе с визуальным Gantt-компонентом.

## 10.2. Интервалы

`startDate` и `endDate` включительны.

Пример:

- start: 2026-07-20;
- end: 2026-07-22;
- при рабочем календаре Пн–Пт duration = 3.

## 10.3. Finish-to-Start

Для связи `A → B` с lag 0:

`B.startDate >= nextWorkingDay(A.endDate)`.

Для lag N:

`B.startDate >= addWorkingDays(nextWorkingDay(A.endDate), N)`.

## 10.4. Multiple predecessors

Минимально допустимая дата successor равна максимуму ограничений всех его predecessors.

## 10.5. Cascade move

Вход:

- selected stage IDs;
- delta в рабочих днях;
- тип операции move/resize;
- calendar;
- graph;
- locked stages.

Алгоритм:

1. Проверить, что selected stages не locked.
2. Построить множество транзитивных successors.
3. Получить topological order затронутого subgraph.
4. Применить delta к selected stages.
5. Применить delta к successors, не входящим в selected, сохраняя duration.
6. Для каждого этапа в topological order вычислить minimumStart по всем predecessors.
7. Если start раньше minimumStart, сдвинуть этап вправо до minimumStart.
8. Если необходим сдвиг locked stage, остановить операцию и вернуть conflict result.
9. Пересчитать `quarterIds`, duration и capacity deltas.
10. Вернуть patch, inverse patch и change summary.

## 10.6. Resize

- resize правой границы меняет endDate и duration;
- resize левой границы меняет startDate и duration;
- duration не может быть меньше одного рабочего дня;
- milestone не resize-ится;
- в Cascade successors получают delta изменения окончания этапа, затем нормализуются;
- в Free меняется только этап.

## 10.7. Multi-select move

Выбранные этапы рассматриваются как одна группа:

- относительное расстояние между ними сохраняется;
- этап, выбранный внутри цепочки вместе с predecessor, не сдвигается дважды;
- successors вне selection каскадируются один раз;
- после применения выполняется общая topological normalization.

## 10.8. Free mode conflicts

Free mode не блокирует операцию из-за нарушения dependency. После commit создаётся вычисляемый conflict:

```text
successor.startDate < minimumAllowedStart
```

Conflict не хранится как отдельная истина, а пересчитывается из актуальных данных.

## 10.9. Циклы

При добавлении link используется DFS/Kahn validation. Любой цикл отклоняется до commit.

## 10.10. Детерминированность

Одинаковое исходное состояние и команда обязаны всегда давать одинаковый результат независимо от порядка записей в IndexedDB или DOM.

## 11. Точные правила capacity

## 11.1. Person assignment

Для рабочего дня `d` этапа:

`personLoad(d) += assignment.allocationFte`.

## 11.2. Role assignment

`roleDemand(d) += units × allocationFte`.

## 11.3. Role capacity

`roleCapacity(d) = сумма baseCapacityFte активных сотрудников, имеющих эту роль`.

Чтобы не считать человека дважды при нескольких ролях, сотрудник входит в capacity строки своей primary role по умолчанию. Дополнительные роли используются для фильтрации и назначения, но не увеличивают общую ёмкость автоматически.

В Settings пользователь может изменить primary role.

## 11.4. Role load

`roleLoad(d) = directPersonLoadForPrimaryRole(d) + unassignedRoleDemand(d)`.

## 11.5. Person overload

`personUtilization(d) = personLoad(d) / personCapacity(d)`.

## 11.6. Role overload

`roleUtilization(d) = roleLoad(d) / roleCapacity(d)`.

Если capacity = 0 и load > 0, utilization считается бесконечной/critical, но в UI отображается `нет capacity`.

## 11.7. Person-days

Для периода:

`assignedPersonDays = Σ dayLoadFte` по рабочим дням.

`availablePersonDays = Σ dayCapacityFte`.

`utilization = assignedPersonDays / availablePersonDays`.

## 11.8. Параллельная работа

Этапы могут пересекаться без системного конфликта. Конфликтом является только превышение resource capacity или нарушение dependency.

## 11.9. Cache расчётов

Capacity рассчитывается для выбранного окна и кэшируется по ключу:

```text
workspaceRevision + quarterIds + calendarRevision + resourceRevision
```

При изменении этапа пересчитываются только затронутые дни и ресурсы, но допустима полная O(stages × days) реализация на первом этапе, если она укладывается в performance budget.

## 22. Риски и способы снижения

### Риск 1. DHTMLX Community не содержит нужного auto-scheduling/resource/baseline

**Решение:** заранее считать эти возможности частью собственного domain-слоя. DHTMLX используется как visual interaction engine, а не как полноценный PM backend.

### Риск 2. Расхождение внутреннего состояния widget и Pinia

**Решение:** adapter, command bus и односторонний data flow. Widget не пишет в БД напрямую.

### Риск 3. Непредсказуемые массовые сдвиги

**Решение:** два явно видимых режима, ghost-preview, summary изменений, atomic undo, locked-stage conflict dialog.

### Риск 4. Двойной учёт capacity ролей и людей

**Решение:** конкретная формула role load; primary role для person capacity; role assignment трактуется как дополнительный незакреплённый demand.

### Риск 5. Потеря данных браузера

**Решение:** IndexedDB, persistent storage request, rolling backup, явный статус autosave, регулярное напоминание об экспорте при отсутствии свежего export.

### Риск 6. Слишком большой PNG

**Решение:** viewport export, выбор диапазона/эпиков, разбиение на страницы, print-to-PDF.

### Риск 7. Квартальное разделение ломает cross-quarter dependencies

**Решение:** canonical stage хранится один раз, `quarterIds` является индексом видимости, связанные boundary records подгружаются по запросу.

### Риск 8. Scope creep из checklist-задач

**Решение:** tasks не получают даты и capacity в MVP. Детализированная задача должна быть преобразована в stage.

## 23. Будущее развитие

При появлении backend архитектура должна позволить заменить repositories, не переписывая domain engine.

Приоритетные расширения:

1. server sync и shared workspace;
2. авторизация и read-only links;
3. интеграции с YouTrack/Jira/GitHub;
4. индивидуальные календари, отпуска и part-time schedule;
5. fixed-work/fixed-duration scheduling;
6. автоматическое распределение role demand;
7. start-to-start и другие dependency types;
8. cross-epic dependencies;
9. critical path;
10. saved views;
11. comments/change log;
12. CSV/Excel import;
13. PWA/offline installation;
14. multiple workspaces;
15. server-generated PDF.

## 24. Definition of Done

Функция считается готовой, если:

- реализованы acceptance criteria;
- есть unit/component/E2E tests по критическим сценариям;
- нет TypeScript и lint errors;
- изменения модели имеют migration;
- операции проходят через command layer;
- данные сохраняются транзакционно;
- проверена работа в Chrome, Edge и Safari;
- UI имеет loading, empty, error и conflict states;
- обновлена пользовательская документация;
- не добавлены скрытые сетевые запросы;
- performance budget не нарушен;
- feature прошла code review и ручную проверку на workspace с 500 этапами.

## 25. Финальная рекомендация по MVP

Для первой рабочей версии не следует пытаться сделать «маленький Microsoft Project». Главная ценность инструмента — быстрый визуальный delivery-план и прозрачный capacity.

MVP должен идеально решать четыре операции:

1. набросать этапы на квартал;
2. связать их в последовательные и параллельные ветки;
3. безопасно сдвинуть план каскадом или свободно;
4. увидеть, где команда перегружена или имеет запас.

Baseline, Markdown, checklist и экспорт дополняют эту основу, но scheduling engine, data safety и понятное поведение drag являются наиболее критичными частями продукта.
