# Production-эксплуатация

## Развёртывание

Используйте один экземпляр Express и локальный persistent volume для SQLite. Требуется Node.js 24; приложение запускается за HTTPS reverse proxy. Команды сборки и Compose приведены в [README](../README.md). Установите `PUBLIC_ORIGIN` равным точному HTTPS origin, который видит браузер, и проксируйте запросы к порту `3101`. `TRUST_PROXY=1` предназначен для одного доверенного proxy.

Перед выпуском выполните `bun run typecheck`, `bun run lint`, `bun run test`, `bun run test:performance`, `bun run test:e2e` и `bun run build`. Прямые вложенные ссылки обслуживает Express; `/api/*` никогда не возвращает SPA HTML.

## Создание и управление workspace

Создавайте workspace только командами `workspace:create`, `workspace:list`, `workspace:reset-pin` из [README](../README.md). PIN вводится скрыто в терминале, код генерируется случайно. Смена PIN отзывает все активные разрешения на редактирование. Распространяйте код и PIN раздельно согласно внутренним правилам команды.

## Резервные копии

Встроенные снимки защищают от ошибочного изменения одного workspace. Для отказа диска или повреждения файла ежедневно запускайте `backup:database --output /data/...` и сохраняйте созданный файл вне volume. Команда использует SQLite backup API и может выполняться во время работы приложения. Раз в релиз проверяйте восстановление на отдельном экземпляре, не на рабочей БД.

## Выпуск и перенос

1. Скопируйте рабочую БД и отдельно проверьте восстановление копии.
2. Проверьте v1/v2/v3 JSON на тестовом workspace.
3. На прежнем origin скачайте локальный JSON либо перенесите IndexedDB через экран «Данные и backup». Не очищайте прежнее хранилище.
4. Запустите новый выпуск и проверьте `/health`, открытие по ссылке с другого устройства, PIN, запись и конфликт двух редакторов.
5. Перезапустите сервер и убедитесь, что workspace, сессии и снимки сохранены.

## Инциденты

При `409` редактор видит новую версию; скачайте неподтверждённый черновик при необходимости и загрузите данные сервера. При разрыве связи можно повторить тот же запрос с прежней версией: если первая запись успела завершиться, ответ будет `409`, без перезаписи. При `413` уменьшите импорт или согласованно измените `JSON_LIMIT`. При `429` дождитесь срока из `Retry-After`. Ошибки сервера логируются без содержимого планов, PIN и токенов.
