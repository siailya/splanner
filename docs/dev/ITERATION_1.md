# 2. Итерация 1 — Planning Core

## 2.1. Цель

Создать первую полноценно используемую версию, которая заменяет Excel-таймлайн для планирования эпиков и этапов. Пользователь должен иметь возможность создать план, расположить этапы на календаре, связать их зависимостями, переносить цепочки и сохранять данные локально.

После завершения итерации приложение уже можно использовать для реального квартального планирования, но без расчёта загрузки команды, baseline и расширенного sharing.

## 2.2. Пользовательский результат

Пользователь может:

1. Открыть SPA без регистрации и создать локальный workspace.
2. Создать несколько эпиков.
3. Создать внутри эпиков `task`, `scope` и `milestone`.
4. Видеть месяц, дату, день недели, выходные и текущий день.
5. Перетаскивать этапы и изменять их длительность.
6. Создавать Finish-to-Start зависимости.
7. Создавать параллельные ветки внутри одного эпика.
8. Переносить связанную цепочку в режиме `Каскад`.
9. Перемещать только выбранный этап в режиме `Свободно` и видеть конфликт зависимости.
10. Работать с текущим, следующим и совмещённым представлением двух кварталов.
11. Перезагрузить страницу без потери данных.
12. Выгрузить workspace в JSON и восстановить его обратно.

## 2.3. Объём работ

### 2.3.1. Technical spike и подтверждение технологических решений

Spike входит в начало итерации и является обязательным quality gate.

Необходимо:

- поднять Nuxt SPA через Bun;
- подключить Nuxt UI;
- подключить DHTMLX Gantt Community;
- отрисовать тестовый набор из 500 этапов и 1 500 связей;
- проверить drag, resize, создание/удаление links;
- проверить custom templates/styles;
- проверить smart rendering;
- подтвердить синхронизацию событий Gantt → application command → Pinia → Gantt;
- измерить latency drag/resize и базовый FPS;
- зафиксировать ограничения Community Edition;
- принять окончательное решение о DHTMLX как visual engine.

**Выход spike:** короткий ADR с результатами, ограничениями и подтверждённой схемой интеграции.

### 2.3.2. Основа приложения

Реализовать:

- Nuxt SPA (`ssr: false`);
- основную layout-структуру;
- роут `/timeline`;
- базовые разделы навигации с disabled/placeholder состояниями для будущих экранов;
- Pinia stores;
- error boundary и глобальные toast-уведомления;
- светлую и тёмную тему;
- desktop-first layout;
- сохранение UI preferences в `localStorage`.

### 2.3.3. Domain-модель первой версии

Реализовать и покрыть тестами сущности:

- `Workspace`;
- `Quarter`;
- `Epic`;
- `Stage`;
- `ActivityType`;
- `Dependency`;
- `WorkingCalendar`;
- базовые заготовки `Resource`, `Assignment`, `WorkItem`, `Baseline`, но без полноценного UI;
- `Command` / `Patch` для изменяющих операций.

Поля этапа, обязательные в итерации 1:

- `id`;
- `epicId`;
- `title`;
- `kind: task | scope | milestone`;
- `activityTypeId`;
- `startDate`;
- `endDate` или milestone date;
- `status: planned | inProgress | done | blocked`;
- `locked`;
- `sortOrder`;
- `quarterIds`;
- timestamps.

### 2.3.4. Рабочий календарь

Реализовать:

- выбор рабочих дней недели;
- список нерабочих дат;
- список дополнительных рабочих дат;
- функции `isWorkingDay`, `addWorkingDays`, `workingDaysBetween`, `nextWorkingDay`;
- пересчёт отображаемой длительности по рабочим дням;
- визуальное выделение нерабочих дней;
- безопасную работу с локальными датами формата `YYYY-MM-DD` без timezone drift.

Изменение календаря в итерации 1 должно запускать контролируемый пересчёт дат. Перед применением показывается количество затрагиваемых этапов.

### 2.3.5. Persistence

Реализовать IndexedDB через Dexie:

- schema version 1;
- таблицы workspace, quarters, epics, stages, dependencies, activityTypes, calendar, settings;
- repositories;
- транзакционные изменения связанных сущностей;
- lazy loading кварталов;
- autosave;
- индикатор `Сохранено / Сохранение / Ошибка`;
- восстановление состояния после reload;
- начальную миграционную инфраструктуру.

`localStorage` не используется для хранения рабочих данных.

### 2.3.6. Эпики

Реализовать:

- создание;
- переименование;
- изменение цвета/маркера;
- сортировку;
- сворачивание/разворачивание;
- архивацию;
- удаление с подтверждением;
- отображение агрегированного периода эпика по его этапам;
- создание этапа внутри конкретного эпика.

Отдельная полноценная страница эпика не входит в итерацию 1; достаточно drawer/compact details.

### 2.3.7. Этапы и Timeline

Реализовать:

- строку эпика и вложенные строки этапов;
- day scale с месяцем, числом и днём недели;
- sticky header;
- sticky левая панель;
- горизонтальный и вертикальный scroll;
- выделение текущего дня;
- отображение task/scope/milestone;
- цвет по activity type;
- статусное оформление;
- tooltip;
- создание этапа через форму;
- создание этапа drag по пустому диапазону;
- drag по горизонтали с day snapping;
- resize с обеих сторон;
- изменение порядка строк;
- перенос этапа между эпиками;
- блокировку этапа;
- drawer редактирования основных полей;
- простые фильтры по эпику, виду, activity type и статусу;
- поиск по названию.

### 2.3.8. Scheduling engine

Реализовать собственный TypeScript engine:

- Finish-to-Start зависимости;
- несколько predecessors/successors;
- lag в рабочих днях;
- ацикличный граф;
- topological ordering;
- валидацию циклов до сохранения связи;
- параллельные независимые ветки;
- `Cascade` move;
- `Free` move;
- временное переключение режима через `Alt/Option`;
- пересчёт при resize;
- conflict detection;
- visual preview затрагиваемой цепочки до drop;
- обработку locked successors;
- межквартальные связи;
- детерминированный результат пересчёта.

В режиме `Каскад` одна пользовательская операция должна создавать одну команду в истории изменений, независимо от числа сдвинутых этапов.

В режиме `Свободно` действие не блокируется из-за нарушения зависимости, но конфликт явно отображается.

### 2.3.9. Базовый undo/redo

В итерации 1 обязательны:

- undo/redo для создания, удаления и редактирования эпика/этапа;
- undo/redo drag и resize;
- undo/redo создания/удаления зависимости;
- атомарная отмена каскадного переноса;
- `Ctrl/Cmd + Z` и `Ctrl/Cmd + Shift + Z`;
- минимум 50 операций истории в рамках сессии.

Персистентная между перезагрузками история не требуется.

### 2.3.10. Кварталы

Реализовать:

- текущий квартал;
- следующий квартал;
- совместный диапазон current + next;
- загрузку архивного квартала по выбору;
- этап как один canonical object, даже если он пересекает два квартала;
- `quarterIds` как индекс пересечения;
- отсутствие дублей на совмещённом timeline;
- сохранение выбранного режима просмотра.

### 2.3.11. Минимальный JSON import/export

Поскольку приложение уже используется для реальных данных, базовая переносимость не откладывается до третьей итерации.

Реализовать:

- экспорт полного workspace в один JSON;
- поля `schemaVersion`, `application`, `exportedAt`;
- импорт только в режиме полной замены;
- schema validation;
- предварительное подтверждение замены;
- автоматический in-memory backup перед импортом;
- откат, если импорт не прошёл;
- отсутствие частично импортированного состояния.

Merge import, управление snapshots и экспорт квартала появятся в итерации 3.

## 2.4. Что не входит в итерацию 1

- сотрудники, роли и assignments в пользовательском UI;
- capacity panel;
- Markdown editor;
- внутренние work items;
- multi-select и массовые операции;
- copy/paste и дублирование;
- полноценная страница эпика;
- baseline;
- table view;
- PNG/PDF export;
- пользовательские backup snapshots;
- расширенный import preview/merge;
- accessibility hardening;
- финальная оптимизация Safari.

## 2.5. Критерии приёмки итерации 1

1. Пользователь создаёт эпик и три этапа разных видов.
2. Timeline корректно показывает месяц, число, день недели, выходные и текущий день.
3. Task/scope перемещаются на целое число дней и снапятся к календарю.
4. Resize корректно меняет рабочую длительность.
5. Milestone не получает duration и не участвует в capacity-заготовках.
6. Finish-to-Start связь визуализируется и ограничивает schedule.
7. Циклическую зависимость создать нельзя.
8. Две параллельные ветки одного эпика имеют пересекающиеся даты без ложного конфликта.
9. В `Cascade` перенос predecessor сдвигает транзитивных successors одной операцией.
10. В `Free` двигается только выбранный этап и показывается конфликт.
11. Locked stage не перемещается неявно без предупреждения.
12. Undo отменяет весь каскад одним действием.
13. Reload восстанавливает workspace.
14. Current, next и combined quarter views работают без дублей.
15. JSON export/import восстанавливает эквивалентный workspace.
16. Ошибочный import не повреждает текущие данные.
17. Smoke-test на 500 этапах подтверждает согласованный performance budget.

## 2.6. Демонстрационный сценарий

Создать эпик `CPM–CPA аукцион` с двумя параллельными ветками, связать этапы, сдвинуть одну ветку каскадно, вторую оставить неизменной, перейти между кварталами, перезагрузить страницу, экспортировать JSON, очистить workspace и восстановить план из файла.
